# codie-claude-plugin — Codie × Claude Code

A Claude Code plugin that **connects Codie devices on your LAN directly** to interactive Claude Code sessions: give Codie a voice instruction → the session carries it out → a spoken-style summary is sent back and read aloud by the device. When Claude Code is waiting for your permission or reply, Codie also reminds you by voice to check the computer.

> Only useful to **Codie device owners**: without a Codie, this plugin does nothing.

```
Codie main app (clt01) — its model calls the ext.* tools ask_agent / cancel_task
                              ⇄ clt01 tool-integrations HTTP + WS, signed with this computer's client credential (agentd is the client)
                         codie-agentd background service (shared by all sessions)
                              ⇄ local loopback HTTP (127.0.0.1, token auth)
                         per-session plugin MCP server (thin client)
                              ⇄ MCP channel / tools / Stop hook
                         interactive Claude Code session
```

## Prerequisites

- **Codie firmware 1.6.0 or later is required.** Pairing must issue a **client credential**, and the device's model must offer external tools (`ext.*`). Earlier firmware versions are not supported; update your Codie before pairing.
- Device and computer are on the **same LAN** (mDNS discovery of the device; the computer connects to the device).
- Node ≥ 20 on PATH.
- Claude Code signed in with **claude.ai** (required by the channels research preview; channels do not work under `-p` / Agent SDK, only in interactive sessions).

## Install

The publishing repo is **CODE27Official/codie-plugin-for-agents** (it is the plugin source for both Claude Code and Codex, generated by `scripts/publish-codie-plugins.sh`; publishing steps are in `docs/runbooks/codie-plugin-publish.md`). Easiest: send the whole "one-step install" block at the top of that repo's README to Claude Code or Codex. It installs the plugin for both on its own; reopen the session and say "set up Codie" (`/codie:setup`), and the wizard runs the checks, pairing and live self-test.

Manual install (in a terminal):

```
claude plugin marketplace add CODE27Official/codie-plugin-for-agents
claude plugin install codie@codie
```

Update: `claude plugin marketplace update codie && claude plugin update codie@codie` (it only updates when the version number changes). Dependencies are bundled into `dist/`, so no `npm install` is needed. For development, install from this repo: `claude plugin marketplace add <this repo>/codie-claude-plugin`.

Launch: a plain `claude` is enough. The plugin ships a **monitor** (`monitors/monitors.json` → `dist/inbox.mjs`): when each interactive session starts, Claude Code runs it in the background; it registers with codie-agentd as that session's inbox and, when a device task arrives, prints a line `[Codie voice task task_id="…" device="…"] …`. Claude Code hands that line to the session as a notification, and **starts a turn on its own to handle it even when the session is idle**. So there is no need to open a channel or say "listen". With several Claude Code sessions open, the task goes to the most recently used one. Monitor limitations (set by Claude Code): it only runs in interactive sessions (not in `claude -p`); Windows needs Git Bash; it is unavailable with Bedrock / Vertex / Foundry or when `DISABLE_TELEMETRY` is set — in those cases fall back to a channel, listening, or background sessions below. `codie_doctor` tells you whether the current session has an inbox.

You can still launch with a channel (research preview; unlisted plugins require this flag):

```bash
claude --dangerously-load-development-channels plugin:codie@codie
```

**When no Claude Code session is open on the computer**: with no inbox, no channel session and no listening session, device instructions go to a **background session** (see "Background sessions" below): if a Codex session is open, the task is put into that Codex session; otherwise a background Claude session is started in the most recently used Claude project directory to run it. You can also still tell Claude "listen to Codie" (or "listen for 30 minutes"); the session claims tasks in a loop per `/codie:listen`, and "stop listening" ends it. If background sessions are turned off and there is no channel or listener, the device immediately hears "No session on the computer is handling Codie" instead of waiting.

## Usage

| Skill | What it does |
|---|---|
| `/codie:pair` | Scan the LAN (about 3 s) → pick a number → the device screen shows a 6-digit code → enter it → paired. Cancelling tells the device to withdraw the code |
| `/codie:setup` | One-step setup: `codie_doctor` checks every prerequisite → fixes whatever is missing (Claude Code side only) → pairing → explains background sessions and usage → live self-test |
| `/codie:status` | Each paired device online/offline + tasks in progress, whether any session is listening, connected sessions |
| `/codie:listen` | Claim device instructions without a channel: check once, or keep listening for a while (default 10 minutes) |
| `/codie:remind` | Show or switch the voice reminder settings: when to remind at the end of a turn (only on a question, the default / every turn), how much Codie says (full, the default / brief), and the voice language (the computer's system language by default) |
| `/codie:unpair` | Remove a device (also drops its connection) |
| `/codie:statusline-setup` | **Manual invocation only** (Claude never triggers it). Writes `🟢 Codie online/paired` into `statusLine` in `~/.claude/settings.json`; backs it up to `settings.json.bak-codie` first, and if a statusLine already exists, asks whether to replace it or add a line. The path changes after plugin updates, so re-run it |

After pairing, agentd publishes `ask_agent` / `cancel_task` to the device within a few seconds. Then tell Codie "have Claude on the computer …", and the session shows `Monitor event: [Codie voice task task_id="…" device="…"] …` (or `<channel source="codie" …>` in a channel session). When Claude is done it calls `codie_reply` to send a one-to-three-sentence spoken summary back to the device. When the device cancels a task, the session receives `[Codie cancel task_id="…"] …`.

**Device tasks are asynchronous**: as soon as the computer takes the task (the push shows up in the inbox or channel session's transcript, or it is queued for a listener), the device's `ask_agent` call immediately returns "The computer has received the task and is working on it; there is no result yet. The result will be announced separately when it is ready, so do not state a result now." plus a note not to call `ask_agent` again (this is the tool result for the device's model; it says explicitly there is no result yet so the model doesn't make one up on the spot). That conversation round ends there and you can ask something else. When the computer finishes, the device speaks the summary as-is (clt01 `agent/results`, sent only to the device that started the task; it waits until the device is idle and is recorded in the chat). Later failures (interruption, session closed, nobody claimed it, timeout) are spoken the same way.

MCP tools (used inside the skills; Claude can also call them directly): `codie_poll`, `codie_listen_stop`, `codie_reply`, `codie_notify`, `codie_remind_mode`, `codie_status`, `codie_list_devices`, `codie_pair_begin`, `codie_pair_confirm`, `codie_pair_cancel`, `codie_unpair`.

## Behavior notes

- **Plain HTTP on the LAN**: agentd talks to the device over `http://` / `ws://`. Every request is signed (HMAC) with the client credential issued at pairing, so the secret itself never crosses the network, but the traffic is not encrypted. **Use it only on trusted home/office networks**, and don't keep a channel-enabled session open on public Wi-Fi.
- **Pairing**: `pair/confirm` returns the device's master secret (`local_secret`); agentd uses it once to have the device issue this computer's **client credential** and never writes it to disk. `pairing.json` keeps only the client credential. A device that issues no credential (old firmware) is not paired, and an existing pairing stays unchanged.
- **Device link**: for each paired device agentd publishes a tool integration (`ask_agent`, `cancel_task`) to clt01 and keeps its tool-integrations WebSocket open; the device's model calls those tools over it.
- **Tasks**: a voice task is an `ask_agent` call. While a device's call is still waiting (not yet taken), another `ask_agent` from the same device is rejected ("The previous task is still running. Please try again later."). A task that is taken answers the call with `accepted` (the tool result for the device's model: handed over, not done, do not call again); if no session has taken it close to clt01's 20-second call limit, the call is answered "Handed to the computer; the result will be announced when it is done." and the task is kept. The device is then free and can take other instructions (one device can have several taken tasks). The final answer is spoken on that task's device; if the device is offline it is not delivered (nothing is kept). If nobody can take it → the call is answered `rejected`. Untaken tasks are cleaned up after 10 minutes; taken tasks last at most 60 minutes, after which "The computer task timed out. Please send your request again." is spoken. `cancel_task` stops a task the device handed over.
- **Stop hook fallback**: when Claude ends a turn without calling `codie_reply`, the plugin replies only to the in-flight task that matches **the channel push that started this turn** (it reads back up to 8 MB from the end of the transcript to find the start of the turn), using the last reply with code blocks/markdown stripped and truncated to about 200 characters. If the user started the turn by typing in the terminal → nothing is sent.
- **Interrupting frees the device**: if you stop the task in the terminal or switch to something else mid-task, the model immediately calls `codie_reply` with the fixed sentence "The task on the computer has stopped. You can tell me again what to do." (spoken as-is). When you press Esc (Claude Code doesn't run the Stop hook), the session process sees `[Request interrupted by user]` in **the transcript file that recorded the task**, after the task was claimed (Esc in another session in the same project directory doesn't affect it; denying a permission request writes the same marker, which also counts as an interruption), and within about 1 second has agentd end all tasks it holds with that fixed sentence, so the device can take new instructions right away. If the session process is killed outright, agentd notices within about 5 seconds and tells the device "session closed".
- **Reminding the user**: each source is scoped to this session —
  - **Claude speaks first**: before AskUserQuestion, or a reply that ends with a question, Claude calls `codie_notify` with `message`: a spoken summary (under 200 characters) of the question, the options (for fixes: root cause or workaround) and its recommendation, in the voice language. The device reads it as written through clt01 `agent/results`, which also records it in Codie's chat.
  - **End of turn** (Stop hook): follows the reminder mode (`/codie:remind`, stored in `settings.json`) — the default `question` reminds only when the last sentence ends with `?`/`？`; `every_turn` reminds at the end of every turn. Turns that replied to a Codie task have the device read the summary instead, with no reminder; it is also skipped if `codie_notify` was called within the last 30 seconds.
  - **AskUserQuestion** (`PreToolUse` hook): reminds unless Codie spoke within the last 30 seconds (Claude's own `codie_notify`).
  - **Claude Code notifications**: the `Notification` hook (`permission_prompt` permission confirmation / `idle_prompt` idle for about 60 seconds). A permission confirmation says what Claude asks to do: the `PermissionRequest` hook remembers the tool call's own description (or the tool and file name) for the prompt that follows about 6 seconds later. `idle_prompt` fires after every turn, so it follows the reminder mode — the default `question` reminds only when the session's last reply ends with a question (read from the transcript the hook provides), and `every_turn` always reminds.

  Without a message, a reminder is one fixed sentence ("Claude Code on the computer needs you to take a look.") in the voice language (Chinese for `zh-*`, otherwise English), on every online device (clt01 `tts/utterances`). It waits until the device is idle (at most 60 seconds), and utterances to one device go one at a time. The Notification hook skips the reminder if Codie spoke (a summary or reminder) within the last 2 minutes, so an end-of-turn reminder isn't repeated by `idle_prompt` about 60 s later.
  - **Detail** (`remindDetail`): `full` (default) reads Claude's message and the permission request aloud; `brief` speaks only the fixed reminder, so nothing about the session is said in the room.
  - **Voice language** (`voiceLanguage`): `system` (default) follows the computer's locale; or a tag such as `en`. Each session puts it in its MCP instructions at startup, so a switch reaches other open sessions after they restart.

## Background service codie-agentd

Device links, pairing and the task table are all held by one background process, **codie-agentd**, shared by every Claude Code and Codex session; each session's MCP server is just its client.

- **When it starts**: when any session's MCP server starts and finds it isn't running, it launches it in the background (`node <plugin>/dist/agentd.mjs`, detached from the session, so it survives the session exiting). Two sessions starting at once launch only one (`agentd.lock`). A plugin with a newer version makes the old agentd exit and replaces it with its own.
- **When it exits**: after **10 minutes** with no session connected (`CODIE_AGENTD_IDLE_MS`) it exits on its own, and the device then sees the computer as offline. There is no autostart at boot: after the computer restarts, it waits until you open Claude Code or Codex once.
- **Who gets device instructions**: first, push to a session with a channel (if several, the most recently used — one that called a tool or just finished a turn; the session confirms delivery from this project's transcript, a new transcript after `/clear` also counts, and if not confirmed within 8 seconds it reroutes); otherwise, a listening session (`codie_poll` waiting, claimed something within 90 seconds, or has a poll-claimed task not yet replied to); otherwise, a background session (next section); if none work, the device is told immediately "No session on the computer is handling Codie".
- **Logs**: `~/.codie/agentd.log` (rotated to `agentd.log.1` on the next start once it exceeds 5 MB). When a `codie_*` tool in a session reports "Codie background service unavailable/error", look here first.
- **Data directory**: `~/.codie/` (configurable with `CODIE_HOME`), shared by the Claude Code and Codex plugins: a device paired on one side works on the other right away.
- The Stop / Notification hooks send turn info together with their ancestor process chain to agentd, which uses it to find the matching session (Windows doesn't use the ancestor pid chain; see Known limitations).

## Background sessions (no channel, no listening)

When there is no channel session and no session is listening, agentd hands device tasks off itself. **On by default**:

1. **An open Codex session**: through Codex's shared app-server (the socket under `/tmp/codex-daemon-<uid>/`), agentd finds sessions that can accept input and **whose window is still open**, preferring idle ones and, among sessions in the same state, the most recently active; it queues only when all are busy (re-reading the state before sending) (the app-server keeps sessions after their window closes, so only sessions whose directory matches a running terminal `codex` process count; while the Codex desktop app is running, any directory counts), and puts the task into it with `codex queue --thread <session> --message <task>`. Codex starts a new turn right away (if the session is busy, it queues until that turn ends); you can watch it run in that Codex window, and the conversation before and after stays in the same session. Requires a Codex session connected to agentd (plugin loaded).
2. **Otherwise, a background Claude session**: a new background session is started with `claude --bg` in **the project directory of the most recently used Claude Code session** to run the task (`codie_reply` is pre-approved, no confirmation prompt), and once it finishes (goes idle) it is stopped with `claude stop`. To carry over what was said before, the **last 8 device conversations of the day** (question + answer) for the same project are written into the next task's prompt, recorded in `~/.codie/background.json` and cleared the next day. It doesn't use `--resume` to continue the same session: in testing, `claude --bg --resume` starts executing before the plugin connects, so `codie_reply` isn't available. To see what it did: `claude agents` lists them, `claude attach <id>` opens one. Several tasks arriving at once each get their own session, without waiting on each other.

Automatic Codex delivery routes by intent: a general task prefers an idle session; when the user explicitly asks for an idle session, only idle user sessions qualify, and with no available target the device is told so instead of queueing into a busy session; when a session or project is named, the task always goes to the matching target, queueing even if it is busy; "continue what we were doing" reuses the session that device last delivered to successfully. The last session is stored per device in `routing.json` and survives restarts. If the target is not open or matches several sessions, the candidates are returned for the user to pick explicitly; the task is not redirected to another session. Subagents cannot be targets.

The device's model passes the routing as `ask_agent` arguments: `prompt` (the task), `mode` (`auto` by default, `idle`, `continue` or `session`) and, only with `session`, `target` (a session ID, full name, project directory or directory name). A task without a mode is treated as a general task; intent is never guessed from keywords.

Both ways have the session call `codie_reply` with the task's `task_id` to reply to the device. If it doesn't: for Claude, the Stop hook falls back to the last reply; for Codex, agentd announces the last reply taken from the session log; if there is nothing to announce (after the session has been idle for 15 seconds), the device hears "The session on the computer finished but did not reply with a result. You can say it again." If the session can't start (e.g. `claude` isn't on PATH, or the directory was never trusted), it hears "The computer could not start a session for this task. Please check the computer."; if the task can't be put into Codex, it automatically falls back to a background Claude session. Tasks whose channel push wasn't confirmed within 8 seconds are not passed on to a background session (they may already be running in that session, and running them again would duplicate work); they still get "No session on the computer is handling Codie".

**⚠️ Usage and permissions — adjust as needed:**

- **It consumes your usage**: every device task is a real Claude / Codex turn, counted against your Claude subscription or API usage (same for Codex). Each background Claude session loads the full system context (your CLAUDE.md, plugins, skill list, etc. — in testing a two-sentence session transcript was about 600 KB), so even a very short instruction has a fixed overhead; history only carries the last 8 Q&As, so it doesn't get more expensive over time. Tasks put into a Codex session are charged against that session's context, so the longer the session, the more expensive.
- **Sessions read and write your project and memory as usual**: a background Claude session is an ordinary Claude Code session and follows your CLAUDE.md and auto-memory rules (e.g. if you say "remember …", it may write to `~/.claude/projects/<project>/memory/`).
- **Permissions**: background Claude sessions use your Claude Code permission settings. When an action needs confirmation, it stops and waits for you (Codie reminds you "Claude Code on the computer needs you to take a look."); use `claude attach <id>` to confirm. Don't switch the permission mode to skip confirmations for convenience — device instructions come from the LAN (see the plaintext warning in "Behavior notes").
- **Turning it off**: in `~/.codie/settings.json`, set `"claudeBackground": false` to turn off background Claude sessions, and `"codexQueue": false` to stop putting tasks into Codex sessions. With both off, you're back to "channel and listening only". Changes take effect immediately, no restart needed.

## Configuration and data

| Environment variable | Default | Purpose |
|---|---|---|
| `CODIE_HOME` | `~/.codie` | Data directory (0700), shared by agentd and all sessions |
| `CODIE_AGENTD_IDLE_MS` | `600000` | How long agentd waits with no session connected before exiting |
| `CODIE_AGENTD_UPKEEP_MS` | `30000` | agentd maintenance interval (task cleanup, idle check); shortened only for tests |

Data directory contents:

- `pairing.json` (0600) — one entry per device: `deviceId` / `name` / `host` / `port` / `userId` / `credentialId` / `credentialSecret` (the client credential). Written atomically (temp file + rename).
- `pairing.json.corrupt-<timestamp>` — if `pairing.json` fails to parse it is read as empty, and before the next write the original file is renamed and kept, never silently overwritten.
- `settings.json` (0600) — user preferences shared by all sessions: `remindMode` (`question` / `every_turn`); `claudeBackground` / `codexQueue` (default `true`, see "Background sessions").
- `background.json` — the last 8 device conversations of the day per project directory (`{claude: {<dir>: {day, history: [{q, a}]}}}`), written into the next background Claude task's prompt; delete it to drop the history.
- `status.json` (0600) — written live by agentd: `mode` (`active` / `stopped`), `online`, `paired`, `devices`, `tasks`, `sessions` (number of connected sessions), `sessionPid` (agentd's own pid), `updatedAt`. If the `sessionPid` process is gone, the status line treats it as invalid.
- `agentd.json` (0600) — the running agentd: loopback IPC port, token, `pid`, `version`. Sessions and hooks use it to find agentd; it is deleted when agentd exits.
- `agentd.log` / `agentd.log.1` — agentd logs.
- `agentd.lock`, `agentd.min-version` — the launch lock and version floor (written when agentd is upgraded; for 30 seconds it stops older plugins from relaunching the old agentd, then expires automatically). No manual handling needed.

## Known limitations

- **Results are not kept for offline devices**: a final answer for a device that is offline is dropped. After a result is spoken on a device, end-of-turn and Notification reminders are not sent to that device within the dedup window (30 s / 120 s), so they don't talk over the result.
- **Spoken texts are at most 200 characters**: the device drops longer ones, so the plugin truncates every result and reminder to within 200 characters, ending with "…".
- **Only tasks started by Codie can get a summary back** (`result` must carry a taskId); tasks started in the terminal can only play a fixed reminder via `codie_notify`, without content.
- **Windows doesn't use the ancestor pid chain**, so hooks can't tell which session sent them; with multiple sessions, end-of-turn fallbacks and reminders may be matched to the wrong session (the fallback is still limited by "the task_id must appear in the transcript").
- Channels are a research preview: they require `--dangerously-load-development-channels` + claude.ai sign-in, interactive sessions only. Without a channel, use listening or background sessions.
- **Background sessions rely on experimental features of both CLIs**: Codex's `codex queue` / shared app-server (`[experimental]`), and Claude's `claude --bg`. If a CLI upgrade changes their behavior, background sessions may stop working (the device hears "could not start"), but listening still works. Whether the Codex desktop app uses the same shared app-server hasn't been verified; a background task interrupted in a Codex window is only released after the 15-second "no reply".
- The task table lives only in agentd's memory: tasks in progress are lost when agentd exits (including upgrades).
- Assumption awaiting confirmation on real hardware: Claude Code fires the `Notification` hook with the `permission_prompt|idle_prompt` matcher and the payload carries `notification_type` (the hook script → plugin → device path is verified on real hardware; payloads without a type also trigger reminders).
- Assumption awaiting confirmation on real hardware: when the Stop hook fires, this turn's channel message (including task_id) has already been written to the transcript; if not, the fallback degrades to "send nothing", leaving only `codie_reply`.

## Troubleshooting

- **Check status**: `cat ~/.codie/status.json`. If `mode` isn't `active` or `sessionPid` (agentd) has exited → agentd isn't running; opening a Claude Code session launches it again.
- **agentd log**: `~/.codie/agentd.log` (e.g. `agentd ready`, `announce to … failed`).
- **Session log**: each session's MCP server stderr (prefixed `[codie]`, e.g. `registered with agentd`, `session ready (claude, channel)`) is in Claude Code's MCP log; launch with `claude --debug` to see it.
- **A tool reports "A newer Codie plugin is starting the background service; try again shortly. If this keeps happening, update this plugin."**: a session running a newer version of the plugin just upgraded agentd, and the `~/.codie/agentd.min-version` it wrote stops older plugins from relaunching the old agentd for 30 seconds (preventing the two versions from replacing each other back and forth). Wait a few seconds and retry; the floor expires after 30 seconds. If it keeps happening, a newer-version session keeps upgrading agentd — update this plugin to the same version.
- **Device shows offline**: make sure it is on and on the same Wi-Fi as the computer; on macOS also allow the terminal or app under System Settings → Privacy & Security → Local Network. If the device rejects the credential (it was reset, or this computer was removed on the device), pair again.
- **`/codie:pair` lists no devices**: make sure the device is on and on the same subnet, and the router doesn't isolate mDNS (AP isolation).

## Development

```bash
npm install
npm test                 # node --test
npm run build            # src/ → dist/ (esbuild bundle, dependencies included)
claude plugin validate .
```

`.mcp.json` / hooks / status line all run **`dist/`**, so after changing `src/` you must `npm run build` and commit `dist/` too (installing just clones the repo and never runs npm). CI checks that `dist/` matches `src/`.

**Maintenance rule for agentd changes**: any change to agentd's behavior or IPC must bump `AGENTD_VERSION` (`src/daemon/version.mjs`); otherwise new sessions just reuse the old running agentd and the change doesn't take effect. The Codex plugin bundles its own `dist/agentd.mjs`, so when shared code changes, **build and publish both plugins together** (`cd ../codie-codex-plugin && npm run build`); otherwise whichever side starts first serves sessions from both.

Debugging unpublished changes locally: `claude plugin marketplace add <path to this repo>`, then install and launch as above. Changes to agentd code only take effect once the old agentd exits (wait for it to exit when idle with no sessions, or `kill $(node -p "require('$HOME/.codie/agentd.json').pid")`).

Running manually (without Claude Code):

```bash
export CODIE_HOME=$(mktemp -d)
node dist/server.mjs     # stdin/stdout is MCP; launches agentd in the background
```

A temporary `CODIE_HOME` starts with no pairings, so real devices are left alone. When done, send `POST /shutdown` to agentd (port and token are in `$CODIE_HOME/agentd.json`) to make it exit.
